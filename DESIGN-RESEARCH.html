Making every branch easier to explore

An ancestor-first tree, a compact descendant list, and profiles that open only when needed are the best fit for this family's records. These choices give the branches more space while retaining photographs, evidence and a path for corrections.

This review used official product documentation and W3C accessibility guidance. It compares interface patterns; it is not independent verification of Bhusal genealogy. No paid account, domain purchase or commercial genealogy subscription is required to use this static website.

What the research showed

FamilySearch: begin with the earliest ancestor

The First Ancestor view places an early ancestor above descendants and makes the lineage path visible. That suits a chronicle beginning with Musu. This redesign adopts the ancestor-first arrangement and numbered generations. It preserves daughters and their recorded descendants; FamilySearch's patrilineal clan-path convention is not imposed on this family.

The website's descendancy view uses an expandable vertical list, generation limits and portrait/spouse controls. A compact outline is useful when a wide chart becomes awkward. Gramps Web: focus and navigation

Gramps Web separates chart modes and provides home/back controls around a selected person. Our branch selector, path back to Musu, generation limit and reset control help readers stay oriented. A portrait occupies an on-demand profile instead of a permanent side panel.

Ancestry: match the view to the question

Ancestry distinguishes vertical family exploration from horizontal ancestor-oriented viewing and offers search, zoom and profile navigation. Our two directions show the same descendant relationships. Changing direction never changes the people represented. Search opens a person's profile and offers a way to locate their branch.

MyHeritage: no single chart shows everything

Family, pedigree, list and fan views serve different purposes. An ancestor fan is attractive but would not be the clearest primary view for all of Musu's descendants, siblings and spouses. We use a descendant chart and searchable directory; photographs remain available without consuming the tree's width.

How these findings changed this website

  • More room for branches. The desktop green rail is 88 pixels wide. Profiles and photographs open in a dialog with Family, Details/photo and Sources tabs. The chart occupies the main workspace.
  • Two ways to read. A top-down chart starts with Musu and the Hari Prasad and Damodar branches. A sideways option accommodates another reading preference. The expandable outline offers an alternative to panning a large diagram.
  • Progressive expansion. Start with two generations, expand individual branches, or choose more generations. Opening every branch at once is available, but the resulting chart necessarily requires scrolling.
  • Evidence close to names. Profiles link to original workbook cells. Blank names and ambiguous records carry review markers. “स्व.” appears only for records explicitly marked deceased; missing information does not establish that someone is living or deceased.
  • Maintainer review. A pen button on each card opens a request for that person. The request carries the permanent record ID, generation and branch link. It prepares an email to the maintainer; a relative must send it. Requests never automatically modify the family tree.
  • Room for history. News, planned culture/history subjects and photographs have separate tabs. The earlier ancestor sequence from the first workbook sheet is shown as a sourced heritage note while the interactive tree begins with Musu.

Phone usability and accessibility

W3C reflow guidance expects ordinary content to fit a 320 CSS-pixel width; a spatial diagram may need its own two-dimensional scrolling region. Here navigation, profiles and forms reflow while the chart scrolls within its own area. A green bottom menu replaces the desktop rail. The outline is the easier reading option on narrow screens. W3C Reflow.

Controls generally aim for approximately 44-pixel touch areas, visible keyboard focus and labels. WCAG 2.2's AA minimum target-size criterion is 24 pixels with exceptions, so 44 pixels is a design choice, not a claim about that minimum. Native scrolling, buttons and the outline provide alternatives to mouse dragging. Reduced-motion preferences are respected. These checks are practical verification, not a formal accessibility certification. Target Size; Dragging Movements.

Data quality, privacy and maintenance

The new register contains 542 records: 363 lineage entries and 179 spouses, including unnamed placeholders. It includes 388 source entries from Tikaram's workbook. The main sheet's repeated ancestors are combined; identical names in different families remain separate. Nepali spellings follow the workbook. Romanized labels are search aids, not certified English spellings.

142 records still need clarification, including unnamed spouses and ambiguous entries. For example, “सुदन मोनालिसा” and “भिम रीता” lack a clear separator. A grandson mentioned without his intermediate parent is retained in a note without an invented direct-child connection. These limitations should be resolved through family review.

Phone numbers are removed from the public data, source excerpts and new register. The original workbook and photograph are not bundled with the website. The maintainer's Gmail address is public by request. Browser-added photo previews stay in that browser; shared photographs require an approved image file uploaded with the website.

This remains a static GitHub Pages site: there is no login, database, automatic Excel import or submission inbox. The maintainer reviews emails, updates the register and publishes revised website files. Reliable dates and location evidence are needed before adding a historical timeline or map.
